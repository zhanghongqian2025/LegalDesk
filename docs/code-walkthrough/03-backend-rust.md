# 03｜后端 Rust、Tauri 与 Pi RPC 逐段导读

> 审计基线：提交 `a60f366`（`feat: rebuild LegalDesk as a controlled Pi workbench`），复核日期 2026-08-13。本文行号对应这个提交；后续修改源码后应同步更新行号和结论。

## 1. 先给结论

当前后端已经具备一个可工作的最小大模型接入闭环：Tauri 命令接收案件与任务，Rust 校验用户明确勾选的材料，把允许的 UTF-8 文本预读为内存快照，以 JSONL 通过 stdin 交给固定版本 Pi RPC，消费 stdout 事件，将运行、原始事件和待复核草稿写入 SQLite，并向前端推送实时事件。

最重要的安全选择是：**Pi 以 `--no-tools --no-approve` 启动**。因此，模型没有 `read`、`grep`、`find`、`ls`、shell 或写文件工具；案件材料不是靠 Pi 自行访问，而是由 Rust 在启动前完成数据库归属、规范路径、类型、编码和容量检查后注入提示。这避免把 Pi 的 `current_dir` 误当作文件系统沙箱。

不过，这仍不是完整的生产级隔离：

- `--no-tools` 限制的是智能体工具，不是操作系统进程权限。被替换或恶意的 Pi 可执行文件仍继承 LegalDesk 进程用户的文件和网络权限。
- 运行时只检查 `--version` 文本是否为 `0.84.1`，没有校验可执行文件签名或哈希；`LEGALDESK_PI_BINARY` 可指向任意本地程序。
- `ready: true` 只代表 Pi 二进制版本匹配，不代表模型提供商、凭据、网络或本地模型已经可用。
- 案件文件、SQLite、Pi session 和备份 JSON 都是明文；把内容发送到何处取决于用户的 Pi provider 配置，不能据此宣称“推理离线”。
- 数据备份当前只保存材料元数据和受管文件名，不包含材料文件字节，不能作为完整案件归档。
- 单元测试覆盖了六个关键纯逻辑点，但没有真实/模拟 Pi RPC、取消、超时、数据库故障和备份恢复的集成测试。

## 2. 后端请求路径

```text
React invoke
  -> Tauri command
  -> Rust 参数、UUID、案件归属与路径校验
  -> SQLite / 案件受管目录
  -> Rust 读取选定文本快照
  -> Pi 0.84.1 RPC（无工具、无审批）
  -> JSONL 原始事件落库 + 规范化事件推送前端
  -> completed 时生成 draft / pending 草稿
```

其中 `current_dir` 虽然设置为案件目录，但它只是进程工作目录，不是安全边界；实际的数据最小化边界来自“零工具启动 + Rust 快照”。

### `src-tauri/Cargo.lock`

`Cargo.lock` 第 1–5712 行是 Cargo 自动生成的完整依赖解析，包含直接/传递依赖的精确版本、来源、校验和与依赖关系。它不应手工编辑。仅在有意修改 `Cargo.toml`、执行受控依赖升级或修复安全公告时，由 Cargo 更新并与清单一起评审提交；CI/发布应继续使用 `cargo ... --locked`，避免未经评审的依赖漂移。

## 7. 安全状态与优先级

### 已落实的边界

1. 已移除 Tauri shell/fs 插件，只保留 dialog/opener。
2. 所有案件/材料标识进入文件路径前使用 UUID 校验。
3. 删除、登记和 Pi 材料读取使用 canonical 路径边界，可拒绝已有符号链接逃逸。
4. Pi 零工具启动，并关闭可动态扩展提示/工具面的 extensions、skills、templates、themes、context files。
5. 只有明确选定、同案、受管的 UTF-8 小文本进入模型；不向模型暴露本机绝对路径。
6. 模型输出只能持久化为 `draft/pending`，系统提示要求人工复核。
7. 数据库使用参数绑定和外键；备份导入在单一事务中执行并先验证引用关系。
8. 有材料输入、模型输出、stderr 和运行时间上限。

### 仍存风险

| 优先级 | 风险 | 建议 |
| --- | --- | --- |
| P0 | Pi 可执行文件只验自报版本，不验签名/哈希；零工具不是 OS sandbox。 | 发布时使用受控 sidecar、签名与哈希 pin，并在平台沙箱/独立低权限用户中运行。 |
| P0 | 案件、材料、session、SQLite 与备份均明文，外部 provider 可能接收敏感内容。 | 增加设备静态加密、机构密钥管理、provider 数据边界提示/策略和本地模型部署选项。 |
| P1 | `ready` 不代表 provider/auth/model 可用，当前机器也未安装 Pi。 | 增加最小无材料 health probe 或读取 Pi provider 状态，区分 binary-ready 与 inference-ready。 |
| P1 | 备份不包含材料文件字节，却会恢复材料元数据路径。 | 设计带 manifest、内容哈希、大小限制和加密的归档格式；恢复必须原子恢复 DB + files。 |
| P1 | `persist_event` 吞掉错误，`finish_run` 失败可留下 stale running。 | 将审计失败升级为运行失败、重试/告警，并在启动时对账未终止运行。 |
| P1 | stdout 单行、事件数量、备份 JSON 和大部分字段无资源上限。 | 使用有界 JSONL reader、运行事件预算、备份文件/记录/字段上限。 |
| P1 | stderr 保存 64 KiB 后停止 drain，可能令高噪声子进程堵塞。 | 持续读取到 EOF，只截断内存中保留的诊断文本。 |
| P1 | capability 直接允许前端 `open-path`。 | 用 Rust 命令验证路径属于当前案件后再打开，移除或 scope 原生 opener 权限。 |
| P2 | 文件与数据库跨系统操作不是原子事务，失败会产生孤儿/缺失。 | 使用 staging、补偿删除、操作日志与启动修复扫描。 |
| P2 | 输入值域、长度和 DB CHECK 不完整；查询常静默丢弃坏行。 | 建立统一 DTO validator，增加 CHECK，传播解码错误。 |
| P2 | `update_evidence` 返回 `doc_id: None`，与数据库可能不一致。 | 读取并返回原 doc_id，增加回归测试。 |
| P2 | 没有租户、用户、角色和案件授权。 | 在从单机产品演进到机构协作/私有部署服务前建立身份、RBAC 与案件 ACL。 |

## 8. 测试与验证证据

在上述提交上执行：

```bash
cargo test --locked
```

结果：`6 passed; 0 failed`。覆盖版本解析、agent registry、提示快照标记、备份版本/路径型案件 ID、备份文件名降权和 Unix 符号链接逃逸。

执行：

```bash
cargo clippy --locked --all-targets -- -D warnings
```

结果：未通过，只有两个现存 lint：`lib.rs` 830–840 的 `add_evidence` 有 9 个参数、881–890 的 `update_evidence` 有 8 个参数，触发 `clippy::too_many_arguments`。这不是本次发现的可利用漏洞，但说明命令输入应重构成显式 DTO，也能集中字段校验。

当前测试缺口：

- 没有模拟 Pi 二进制的端到端 JSONL 测试；
- 没有覆盖 `agent_event` 规范化、`agent_settled`、损坏 JSON、超大单行和 2 MiB 输出终止；
- 没有覆盖 abort、kill、10 分钟超时及其竞态；
- 没有 SQLite 落库失败、事件丢失、应用重启 stale run 对账测试；
- 没有备份全量导入、回滚、超大 JSON、文件本体恢复测试；
- 没有材料读取 TOCTOU、文件增长、非 UTF-8、类型拒绝和总量上限的文件系统测试；
- 没有 Tauri capability/XSS 到 opener 的安全集成测试；
- CI 未体现 `cargo audit`/`cargo deny` 一类 Rust 依赖漏洞与许可证策略检查。

## 9. 下一步后端演进顺序

1. 先解决 P0：可信 Pi sidecar/签名、操作系统隔离、数据静态加密和 provider 数据边界。
2. 建立可模拟 Pi RPC 的测试 harness，把正常流、异常流、取消、超时和协议 fixture 纳入 CI。
3. 将审计写入改为强一致或明确告警，并在启动时把遗留 `starting/running` 对账为 interrupted。
4. 设计真正包含材料字节、manifest、hash、加密和大小限制的案件归档格式。
5. 增加受控 PDF/Office/OCR 提取服务；提取结果仍走同样的案件归属、容量、来源和人工复核边界。
6. 用输入 DTO、服务端枚举/长度校验和数据库 CHECK 收紧所有 Tauri 命令。
7. 将系统 opener 包在受管路径命令后，再考虑机构用户、RBAC、案件 ACL 和集中审计。
